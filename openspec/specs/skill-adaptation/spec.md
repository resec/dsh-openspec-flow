# skill-adaptation Specification

## Purpose
Defines how the plugin installs its own OpenSpec workflow skills, replaces the official CLI-oriented skills, and keeps the generated instructions aligned with the tool surface.

## Requirements

### Requirement: Init installs plugin skills without official skills

`openspec_init` SHALL create the project root and write the six plugin skills without generating the official skills.

#### Scenario: Empty project is initialized

- **WHEN** `openspec_init` runs in a directory without an OpenSpec root
- **THEN** the project has `openspec/config.yaml`, `openspec/specs/`, and `.dsh/skills/openspec-*` written by the plugin, and no skill file generated by the OpenSpec CLI

#### Scenario: Existing config is preserved

- **WHEN** `openspec_init` runs in a project that already has `openspec/config.yaml`
- **THEN** the config file is not rewritten and only missing skills are added

### Requirement: Official skill migration backs up first

The plugin SHALL back up an official skill before replacing it, and SHALL keep the backup outside `.dsh/skills` so DSH does not load it as a skill.

#### Scenario: Official skill is replaced

- **WHEN** `openspec_init` finds a skill whose frontmatter names an OpenSpec version
- **THEN** the old file is copied to `.dsh/openspec-flow-backup/<timestamp>/` before the plugin version is written

#### Scenario: Unrecognized skill is found

- **WHEN** a same-named skill has no recognized `generatedBy` value
- **THEN** the tool reports a conflict and does not overwrite it unless `force` is set

### Requirement: Instructions output maps CLI commands to tools

The `openspec_instructions` result SHALL replace known CLI command fragments in the instruction text with the corresponding tool names.

#### Scenario: Proposal instruction is read

- **WHEN** `openspec_instructions` returns the proposal instruction on OpenSpec 1.16.0
- **THEN** the text names `openspec_list`, `openspec_show` and `openspec_validate` instead of `openspec list --specs`, `openspec show` and `openspec validate`

### Requirement: Plugin version refresh is explicit

The plugin SHALL record its version in every generated skill and refresh a skill when that version differs.

#### Scenario: Plugin is upgraded

- **WHEN** `openspec_init` runs after the plugin version changes
- **THEN** skills carrying the older plugin version are backed up and replaced with the current text

### Requirement: User-authored skills are preserved

The plugin SHALL not modify a skill it did not generate unless the caller sets `force`.

#### Scenario: User skill shares a name

- **WHEN** the project has a hand-written `openspec-apply-change` skill
- **THEN** `openspec_init` reports the conflict, leaves the file untouched, and lists the path in its result

### Requirement: Skills use tools and report missing tools

Each generated skill SHALL direct the agent to the `openspec_*` tools for every workflow step and SHALL state that the plugin provides no CLI fallback. When a tool is unavailable, the skill SHALL instruct the agent to report the missing tool and stop.

#### Scenario: Tool surface is present

- **WHEN** the agent loads a generated skill in a session with the plugin tools
- **THEN** every workflow step in the skill names a tool call and no bare `openspec` command is required

#### Scenario: A tool is unavailable

- **WHEN** the agent loads a generated skill in a session without the plugin tools
- **THEN** the skill states that the plugin provides no CLI fallback and the agent reports the missing tool instead of running the CLI
