# Project instructions

This repository develops the `dsh-openspec-flow` plugin. `README.md` covers the tool surface, configuration, and limits; this file covers how work is planned and checked. External contributions follow [CONTRIBUTING.md](CONTRIBUTING.md) and use the CLI-only path there; they do not require the plugin.

## OpenSpec workflow

The project uses OpenSpec. Non-trivial work starts as a change under `openspec/changes/<name>/`:

1. Plan with the installed `openspec-propose` skill, or `openspec_new_change` (the CLI `openspec new change <name>` works too). Read the change's `proposal.md`, `specs/`, `design.md`, and `tasks.md` before editing code.
2. Review the plan before implementing: call `openspec_review` with `action: "start"` and `review: "draft"` (pass the user goal and acceptance conditions as `intent`; `start` is the first round only), read the brief, then submit one report. With `reviewers: 0` submit `action: "self-report"`; with `reviewers: 1` use `action: "wait"` for the independent reviewer. Fix every blocker and continue with `action: "resume"` (no intent) until the review is ready; `openspec_apply_next` refuses while it is not. In a git project, seal the ready draft with a commit that contains only the change directory and, when the plugin wrote it, `openspec/.gitignore`; the first apply refuses a dirty tree, a mixed commit, or artifacts that changed after the draft. Several changes may hold draft reviews at the same time; another change's committed directory is allowed in `HEAD`, but stage only this change. The draft review can be resumed until apply starts; after that it is frozen.
3. Apply with the installed plugin. Load `openspec-apply-change`, then call `openspec_apply_next` once. Apply through archive is serial across changes: while another change holds an apply lock, this change's apply entry is refused and names the holder; draft reviews stay available.
4. After each task or batch, call `openspec_mark_task_done` with `taskIds` for every task finished since the last call and continue with its `next`. Call `openspec_apply_next` again only to start or resync. Run `npm run test:affected -- <paths>` after a batch: it selects the test files importing the modules the batch touched, and the full suite plus `npm run verify` still decide completion.
5. Finish with `openspec_inspect` using `action: "validate"` and `strict: true`.
6. Commit the implementation, run `npm run verify` on Node 24, then review it before archive: call `openspec_review` with `action: "start"` and `review: "apply"` (later rounds use `action: "resume"`), read the brief and diff, and submit the same way as step 2. The verification runs on the committed tree, so a passing run records the coverage stamp the push reuses; a run on a dirty tree writes nothing and costs the next push one rerun. Commit every round before the review. When land refuses a worktree behind main, it records a rebase marker; rebase, retest, resume the apply review for an extra round (`E1`, `E2`) that does not consume a normal round number, and land only after that extra round is ready. A plan change during apply needs the user's written waiver recorded with `openspec_review` (`action: "waive"`, `scope: "plan-change"`, `files`) before editing; apply review then reviews the changed planning artifacts and refuses an unwaived file. Fix every blocker. A project without git has no apply review; say so instead of skipping silently. A successful archive releases the change's apply locks; while another change holds one, archive is refused.
7. A git worktree apply finishes with `openspec_apply_worktree action=land` and `approvedBy: "user"` on the user's explicit request; it merges the worktree branch and commits the archive inside one lifecycle section, then removes the worktree and its local branch while keeping the archived state and landed manifest; a failed cleanup is retried by another land. The maintainer then pushes the merge and archive commits to `origin/main` (`git@github.com:resec/dsh-openspec-flow.git`). A non-worktree change commits the archive, documentation updates and merged specs, then pushes. External contributions stop at their pull request and follow `CONTRIBUTING.md`; they do not push.

In an apply worktree, source the repository development environment before installs and tests: `source <(node <main>/scripts/worktree-env.mjs print)`. It shares npm, pnpm and Chromium caches while keeping `node_modules`, `DSH_HOME` and test output per worktree; see `docs/apply-worktree-dev.md`. These cache and profile paths are repository tooling, not plugin state.

The plugin serves the five workflow skills from its own skill provider at rank 50; it writes no project copy. `openspec_init` only creates the OpenSpec project structure. This repository keeps no `.dsh/skills/` copies. There is no sync-only flow: main specs are updated only by `openspec_archive`, and `openspec-sync-specs` must not be reintroduced.

The plugin also registers a scoped system prompt rule (`openspec-flow:policy`) for agents whose working directory contains an `openspec/` root. It restates these gates: clarify before proposing, confirm before creating a change, review the plan before apply, apply through the compact loop, validate before completion, review the commit before archive, and archive only on request. The rule is advisory and does not restrict tools.

Checkbox state changes go through `openspec_mark_task_done`; that keeps the cached progress and the source line consistent.

## Plugin constraints

- Plain ESM JavaScript with Node built-ins only. Any `@deepseek-ai/*` runtime import or dependency is forbidden; review cards are files under the change's review directory and are served by the review channel.
- `engines.dsh` pins the exact DSH runtime the plugin is verified against, and `engines.node` mirrors that runtime's Node floor; the floor is stated once in the `project-invariants` capability (`Runtime baseline`). When upgrading the DSH dependency, read the target version's `engines.node` first and update both fields together; a mismatch makes DSH skip the bundle.
- Tests and coverage run only on the primary Node major 24 and require a concrete version satisfying `engines.node`. Test and coverage entrypoints check the `node` on `PATH`; they never call fnm, nvm, volta, or read `.nvmrc`. `scripts/bootstrap.sh` is the only entrypoint that may read common global install directories to choose a runtime, and it never invokes a version manager. If the runtime does not qualify, the test entrypoints fail before starting tests.
- The OpenSpec CLI is an exact runtime dependency (`@fission-ai/openspec` 2.0.0, stated by the `project-invariants` `OpenSpec CLI pin` requirement). The plugin resolves only its own installed copy; do not reintroduce `cliPath`, PATH lookup, or project-local lookup.
- Keep tool descriptions and output schemas in `lib/tools/`, the projection and cache in `lib/state.js`, project initialization in `lib/init.js`, packaged-skill discovery in `lib/skills.js` and `lib/skill.js`, and the shipped skills in `skills/` in sync with behavior.
- Every packaged skill's `metadata.generatedBy` must equal `dsh-openspec-flow@<package.json version>`; the skill test enforces it.
- Keep the policy text in `lib/policy.js` consistent with the shipped skills. The policy is agent-scoped and must never be registered globally.
- Add a regression test for every behavior change. The tests use a fake Host context and the real bundled OpenSpec CLI.

## Bundle packaging

The profile installs this repository as a local tarball under `dist/`, not as a linked directory. `npm run bundle:pack` packs the committed `HEAD` content into `dist/dsh-openspec-flow-<version>/` as the tarball plus its `.json` metadata. The entrypoint refuses uncommitted changes outside `openspec/` (uncommitted paths under `openspec/` are reported as ignored, because they cannot enter the tarball), an existing pair without `--force`, a tarball that misses an unconditional core runtime path or carries a test or OpenSpec path, and it leaves `dist/` unchanged on failure. It never writes the profile.

The installed copy is frozen: editing plugin sources does not change it or reload the plugin, and a review completes on the installed version. Repack with `--force` and reinstall (remove the bundle in the Plugins page first, then add the tarball) only when new plugin logic must run. `docs/installing-bundles.md` carries the steps.

## Evaluation harness

- The real-model harness lives in the separate `dsh-openspec-flow-eval` repository together with its spec, fixtures, offline tests and coverage gate. This repository no longer contains `eval/` or `eval:*` scripts.

## Verification

A change is complete when every task is checked, `openspec_inspect` with `action: "validate"` and `strict: true` passes, and `npm run verify` passes on Node 24. That single instrumented run reports both the test summary and the coverage verdict, so a separate plain `npm test` pass is not required. The pre-push hook runs `npm run openspec:check` over every active change and main spec, checks archived task completion, then runs `npm run test:lab -- --mock-only` over the reusable DSH scenarios under `test/lab/` before it decides the coverage step: `node scripts/coverage-stamp.mjs check` may skip `npm run verify` when the last passing enforce run matches, and otherwise the hook runs it. The stamp lives at `.cache/coverage-stamp.json` and is invalidated by a missing or corrupt record, a dirty tree, a fingerprint mismatch on `lib/`, `index.js`, `test/`, `package.json`, `package-lock.json`, `coverage.config.json`, `coverage.baseline.json` or the gate scripts, a moved merge base, or a different Node version. `COVERAGE_SKIP=1` skips only coverage, does not evaluate the stamp, and never skips the lab gate. The lab, its doctor, cache, POC directory and artifacts are documented in `docs/lab.md`. A packaged skill that omits `strict: true` does not lower this repository's gate. The installed plugin runs from the tarball published under `dist/`; editing plugin sources does not change it or reload it. Install a newly packed artifact and restart the session when new plugin logic must run.
