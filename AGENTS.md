# Project instructions

This repository develops the `dsh-openspec-flow` plugin. `README.md` covers the tool surface, configuration, and limits; this file covers how work is planned and checked. External contributions follow [CONTRIBUTING.md](CONTRIBUTING.md) and use the CLI-only path there; they do not require the plugin.

## OpenSpec workflow

The project uses OpenSpec. Non-trivial work starts as a change under `openspec/changes/<name>/`:

1. Plan with the installed `openspec-propose` skill, or `openspec_new_change` (the CLI `openspec new change <name>` works too). Read the change's `proposal.md`, `specs/`, `design.md`, and `tasks.md` before editing code.
2. Review the plan before implementing: call `openspec_review` with `action: "start"` and `review: "draft"` (pass the user goal and acceptance conditions as `intent`; `start` is the first round only), read the brief, then submit one report. With `reviewers: 0` submit `action: "self-report"`; with `reviewers: 1` use `action: "wait"` for the independent reviewer. Fix every blocker and continue with `action: "resume"` (no intent) until the review is ready; `openspec_apply_next` refuses while it is not. In a git worktree apply the plugin seals the draft on the apply branch at the first apply and keeps it off main; the change directory and the plugin-written `openspec/.gitignore` stay uncommitted, and apply refuses genuine dirt, a mixed commit on the worktree-disabled path, or artifacts that changed after the draft. Several changes may hold draft reviews at the same time; another change's committed directory is allowed in `HEAD`, but stage only this change. The draft review can be resumed until apply starts; after that it is frozen.
3. Apply with the installed plugin. Load `openspec-apply-change`, then call `openspec_apply_next` once. Apply through archive is serial across changes: while another change holds an apply lock, this change's apply entry is refused and names the holder; draft reviews stay available.
4. After each task or batch, call `openspec_mark_task_done` with `taskIds` for every task finished since the last call and continue with its `next`. Call `openspec_apply_next` again only to start or resync. Run `npm run test:affected -- <paths>` after a batch: it selects the test files importing the modules the batch touched, and the full suite plus `npm run verify` still decide completion.
5. Finish with `openspec_inspect` using `action: "validate"` and `strict: true`.
6. Commit the implementation, run `npm run verify` on Node 24, then review it before archive: call `openspec_review` with `action: "start"` and `review: "apply"` (later rounds use `action: "resume"`), read the brief and diff, and submit the same way as step 2. The verification runs on the committed tree, so a passing run records the coverage stamp the push reuses; a run on a dirty tree writes nothing and costs the next push one rerun. Commit every round before the review; see Commit conventions for the commit unit. When land refuses a worktree behind main, it records a rebase marker; rebase, retest, resume the apply review for an extra round (`E1`, `E2`) that does not consume a normal round number, and land only after that extra round is ready. A plan change during apply needs the user's written waiver recorded with `openspec_review` (`action: "waive"`, `scope: "plan-change"`, `files`) before editing; apply review then reviews the changed planning artifacts and refuses an unwaived file. Fix every blocker. A project without git has no apply review; say so instead of skipping silently. A successful archive releases the change's apply locks; while another change holds one, archive is refused.
7. A git worktree apply finishes with `openspec_apply_worktree action=land` and `approvedBy: "user"` on the user's explicit request; it fast-forwards main to the reviewed worktree head, commits the archive inside one lifecycle section, then removes the worktree and its local branch while keeping the archived state and landed manifest; a failed cleanup is retried by another land. Online completion for a maintainer change runs `node scripts/pr-publish.mjs --session <id> --apply` from the plugin worktree after the apply review passes, waits for green CI, merges with `gh pr merge --rebase`, runs `node scripts/pr-local-land.mjs verify <n> --session <id>` and `retarget <n> --session <id> --apply` to reset the reviewed worktree branch to the merge commit whose tree equals the reviewed tree, and only then lands. When the merged tree differs from the recorded reviewed tree after a re-review, run `node scripts/pr-local-land.mjs adopt <n> --tree <merged-tree> --session <id> --apply` before verify/retarget; after land, run the same adopt before finish when the landed manifest names another tree, and finish never adopts by itself. Because the land commit is the merge commit already on `origin/main`, the maintainer then runs `node scripts/push-landed.mjs` as a dry run and `--push` to verify the landed manifest and publish only the archive commit to `origin/main` (`git@github.com:resec/dsh-openspec-flow.git`), and records the local phase with `node scripts/pr-local-land.mjs finish <n> --phase pushed --session <id> --apply`, which releases the landing lock; the retarget and finish commands accept the matching owner session without the lock token, and a supplied token must match. See [docs/land-push.md](docs/land-push.md) and [docs/local-pr.md](docs/local-pr.md). Offline completion publishes no pull request: when `preflight` or `pr-publish` reports `offline-land`, run `npm run test:lab -- --mock-only`, land and archive locally with the user's approval, record the offline land with `node scripts/offline-land.mjs record --change <name> --land <sha> --apply` (or record `landed-offline` through `pr-local-land finish` when a local owner entry exists), and stop at local `main` without a push; when GitHub returns, `push-landed --push --offline` publishes the deferred land and archive commits and removes the matching record, and `pr-local-land finish --phase pushed` records `pushed` when an entry exists. Local `main` leading `origin/main` blocks a new online pull request and contributor landing until that push completes. A non-worktree change commits the archive, documentation updates and merged specs, then pushes. External contributions stop at their pull request and follow `CONTRIBUTING.md`; they do not push.

In an apply worktree, source the repository development environment before installs and tests: `source <(node <main>/scripts/worktree-env.mjs print)`. It shares npm, pnpm and Chromium caches while keeping `node_modules`, `DSH_HOME`, the toolchain record and test output per worktree; see [docs/apply-worktree-dev.md](docs/apply-worktree-dev.md). Creating an apply worktree runs `scripts/bootstrap.sh --deps-only` automatically and rolls the worktree back when it fails; the record it writes is never shared with another worktree. These cache, record and profile paths are repository tooling, not plugin state.

A scheduled pull-request review loop lives in `scripts/pr-review-watch.mjs`; `scripts/pr-review-owner-review.mjs` maintains the advisory `owner-review` label, and landing uses `scripts/pr-review-land.mjs`. See [docs/pr-review.md](docs/pr-review.md). The watch polls open PRs, prepares a detached PR worktree, and lets a DSH session run a `pr` review and publish the report as a comment. The owner-review command adds the label when every landing gate except `mergeable` passes and removes it on a head change, a main-induced conflict, a CI regression, the arrival of `mergeable`, or another non-label gate failure; the label never authorizes landing. For a PR with the maintainer-applied `mergeable` label, the landing command syncs a same-repository branch that is behind `main` through GitHub's update-branch API, and `sync-batch` updates every eligible labeled same-repository behind branch in one bounded run without consuming a landing phase, requires the latest `origin/main` before prepare and merge, lets the session review the current head, and runs `gh pr merge --rebase`; the merged tree must equal the reviewed tree before the session archives on main and pushes. A fork branch behind `main` is left to its author. It processes one PR at a time for review and landing, may batch-sync up to 20 labeled same-repository behind branches in one run, never modifies PR code or a fork branch, never force-pushes, writes only `owner-review` and never `mergeable`, and never squashes, creates a merge commit on `main`, or uses admin or force. The landing worktree tolerates other changes' uncommitted planning files but refuses the landing change's own directory, a path outside `openspec/changes/`, a staged index and a non-`main` `HEAD`; `sync` and `sync-batch` do not check the worktree, and the archive command commits only the archived directory, the named `openspec/specs` capability directories and the source deletion with a subject-only commit. It requires an authenticated `gh`, a baseline `main` `openspec/reviews.json` whose `reviews.pr` entry names an enabled tree profile with `reviewers: 1` (passed to the session as `configPath`), and one fixed five-minute scheduled session so the final landing review can resume the reviewer started in that session; a review pass whose re-listing returns the pull request as a not-behind landing candidate continues in the same run through `plan`, `prepare`, `reviewed`, `merge`, archive, push and `finish`, and a ready final review is recorded and merged in the same run, with archive, push and finish completing in that same locked run. Every run reads `node scripts/pr-review-watch.mjs preflight` first. A pull request recorded in `<main worktree>/.cache/pr-review/local-prs.json` is owner-managed: `poll` reports its number as owner-managed but never reviews, prepares, comments on, retargets, lands or merges it, and a local owner holds the cross-session `<main worktree>/.cache/pr-review/landing.lock/` through merge, retarget, land, archive and push. A contributor landing run acquires the same lock, passes its session to the landing commands and releases it at `finish` or when the run stops; a lock held by another session refuses landing and reviews continue. Local `main` leading `origin/main` stops landing and names `push-landed`. The contributor review uses the `pr` entry and `pr-review.json`; the local owner-managed flow keeps `apply-review.json`. The publish, retarget, land, archive-push and offline routes are documented in [docs/local-pr.md](docs/local-pr.md). `state --cleanup` removes closed or merged PR checkouts, and `state --forget <change>` is the operator cleanup when the schedule is stopped.

The plugin serves the five workflow skills from its own skill provider at rank 50; it writes no project copy. `openspec_init` only creates the OpenSpec project structure. This repository keeps no `.dsh/skills/` copies. There is no sync-only flow: main specs are updated only by `openspec_archive`, and `openspec-sync-specs` must not be reintroduced.

The plugin also registers a scoped system prompt rule (`openspec-flow:policy`) for agents whose working directory contains an `openspec/` root. It restates these gates: clarify before proposing, confirm before creating a change, review the plan before apply, apply through the compact loop, validate before completion, review the commit before archive, and archive only on request. The rule is advisory and does not restrict tools.

Checkbox state changes go through `openspec_mark_task_done`; that keeps the cached progress and the source line consistent.

## Commit conventions

One commit per task group, at least. Each numbered `## N.` group in `tasks.md` that changes files owns at least one commit carrying only that group's changes, and no commit combines two groups; the subtasks of one group (for example `1.1`–`1.3`) may share one commit, and a group may take several. A group that only verifies leaves no implementation commit, and a commit that only records checked boxes in `tasks.md` is flow bookkeeping, not a group commit. A commit belongs to the group whose subtasks name the files it changes; when two groups change one file, its message names the group it carries. This covers the implementation commits before the first apply review; a review round's fixes still follow one finding per commit. The repository treats these commit rules as development conventions, not gates: no script, hook or CI check enforces them.

One finding per commit. Every apply review commit answers at most one finding: it carries that finding's fix, or the rework a later round demands, with its regression test when behavior changes, and no other finding's changes. A finding may take several commits, because a later round can overturn an earlier fix; a finding that changes no committed file, such as one deferred, rejected or waived, leaves no commit. Commit a round's findings before the next round opens. This section refines the round-level commit instruction in step 6: several finding-scoped commits still commit the round.

Committed content states the defect, the fix and the reason. Round numbers and extra-round tokens (`round 2`, `E1`), finding ids (`R2-01`, `E1-02`), review record paths and card files stay out of commit messages, change READMEs and every other committed artifact, because a reader of the history cannot resolve them: restate the finding's substance instead. Text that defines or implements these formats may name them. History written before this convention is not retrofitted with these identifiers, and a history rewrite that removes a host path stays allowed.

Commit messages are English. The subject and the body are written in English however the conversation, the change artifacts or an issue are written, and a quoted identifier, file path or command keeps its own spelling.

Commits use the repository identity. A commit created in this repository's working tree takes its author and committer from whatever `git config user.name` and `git config user.email` resolve; do not invent a name, a placeholder address or a bot identity, and pass no `-c user.name`, `-c user.email`, `--author`, `--reset-author`, `GIT_AUTHOR_*` or `GIT_COMMITTER_*` override. If automation ever needs a distinguishable identity, it is configured in the repository and recorded in this section, not supplied per command.

Before the first apply review, read `git log <base>..HEAD` and check that every numbered group that changed files owns a commit carrying only its changes and that no commit combines two groups. Fix a missing boundary before the review opens: commit the group's remaining files, or split the apply branch when its edits went into another commit's patch. The apply review sees the committed tree rather than commit boundaries, so this reading is the check.

Before resuming a round and before land, read the commits made since the round's reviewed base and check that each answers one finding and that no message cites the review; the implementation group commits are exempt.

## Plugin constraints

- Plain ESM JavaScript with Node built-ins only. Any `@deepseek-ai/*` runtime import or dependency is forbidden; review cards are files under the change's review directory and are served by the review channel.
- `engines.dsh` pins the exact DSH runtime the plugin is verified against, and `engines.node` mirrors that runtime's Node floor; the floor is stated once in the `project-invariants` capability (`Runtime baseline`). When upgrading the DSH dependency, read the target version's `engines.node` first and update both fields together; a mismatch makes DSH skip the bundle.
- Tests and coverage run only on the primary Node major 24 and require a concrete version satisfying `engines.node`. Test and coverage entrypoints check the `node` on `PATH`; the pre-push hook may prepend the current worktree's recorded Node, and a recorded pnpm is run with that Node. They never call fnm, nvm, volta, or read `.nvmrc`. `scripts/bootstrap.sh` is the only entrypoint that may read common global install directories to choose a runtime, and it never invokes a version manager. If the runtime does not qualify, the test entrypoints fail before starting tests.
- `pnpm` is pinned by `scripts/toolchain.mjs` to the target DSH release's source `packageManager` and prepared in a shared version bucket; do not add it to `packageManager` or devDependencies. The lab and the pre-push hook read the current worktree's toolchain record.
- The OpenSpec CLI is an exact runtime dependency (`@fission-ai/openspec` 2.2.0, stated by the `project-invariants` `OpenSpec CLI pin` requirement). The plugin resolves only its own installed copy; do not reintroduce `cliPath`, PATH lookup, or project-local lookup.
- Keep tool descriptions and output schemas in `lib/tools/`, the projection and cache in `lib/state.js`, project initialization in `lib/init.js`, packaged-skill discovery in `lib/skills.js` and `lib/skill.js`, and the shipped skills in `skills/` in sync with behavior.
- Every packaged skill's `metadata.generatedBy` must equal `dsh-openspec-flow@<package.json version>`; the skill test enforces it.
- Keep the policy text in `lib/policy.js` consistent with the shipped skills. The policy is agent-scoped and must never be registered globally.
- Add a regression test for every behavior change. The tests use a fake Host context and the real bundled OpenSpec CLI.

## Bundle packaging

The profile installs this repository as a local tarball under `dist/`, not as a linked directory. `npm run bundle:pack` packs the committed `HEAD` content into `dist/dsh-openspec-flow-<version>/` as the tarball plus its `.json` metadata. The entrypoint refuses uncommitted changes outside `openspec/` (uncommitted paths under `openspec/` are reported as ignored, because they cannot enter the tarball), an existing pair without `--force`, a tarball that misses an unconditional core runtime path or carries a test or OpenSpec path, and it leaves `dist/` unchanged on failure. It never writes the profile.

The installed copy is frozen: editing plugin sources does not change it or reload the plugin, and a review completes on the installed version. Repack with `--force` and reinstall (remove the bundle in the Plugins page first, then add the tarball) only when new plugin logic must run. `docs/installing-bundles.md` carries the steps.

## Evaluation harness

- The real-model harness lives in the separate `dsh-openspec-flow-eval` repository together with its spec, fixtures, offline tests and coverage gate. This repository no longer contains `eval/` or `eval:*` scripts.

## Verification

A change is complete when every task is checked, `openspec_inspect` with `action: "validate"` and `strict: true` passes, and `npm run verify` passes on Node 24. That single instrumented run reports both the test summary and the coverage verdict, so a separate plain `npm test` pass is not required. Pull-request CI runs the change and generated-skill checks, `npm run openspec:check`, `npm run check:requirement-length` and `npm run verify`; the change check compares the pull request base with the pull request head, and the length gate applies the review preflight's requirement-description rule before a pull request can enter the watch. `npm run openspec:check` also loads every active change's metadata through `openspec status --change <name> --json`, so an unloadable `.openspec.yaml` fails CI instead of the pull-request review prepare. The pre-push hook reads the pushed remote refs and, when the current worktree has a current toolchain record, puts its Node first on `PATH` so validation and verification run on that runtime; a stale record refuses the push with its correction. A push targeting only `refs/heads/main` runs `npm run openspec:check:push`: it validates main specs and archived task completion and requires every active change to be `in-progress`, so an in-progress change is ignored while a complete or task-less change blocks the push. A push targeting another ref or a mixed set runs `npm run openspec:check` over every active change and main spec. After validation, a push that includes `refs/heads/main` runs `node scripts/check-main-push.mjs` on the main line's local and remote commits: it refuses a direct worktree land and passes a recorded offline range only when `push-landed --offline` set the marker. Then the hook decides the coverage step: `node scripts/coverage-stamp.mjs check` may skip `npm run verify` when the last passing enforce run matches, and otherwise the hook runs it. The local hook does not run the lab scenarios; the remote `lab` CI job guards pull requests and `main`, and the offline local path runs `npm run test:lab -- --mock-only` before its local land. The stamp lives at `.cache/coverage-stamp.json` and is invalidated by a missing or corrupt record, a dirty tree, a fingerprint mismatch on `lib/`, `index.js`, `test/`, `package.json`, `package-lock.json`, `coverage.config.json`, `coverage.baseline.json` or the gate scripts, a moved merge base, or a different Node version. `COVERAGE_SKIP=1` skips only coverage and does not evaluate the stamp. The lab, its doctor, cache, POC directory and artifacts are documented in `docs/lab.md`. A packaged skill that omits `strict: true` does not lower this repository's gate. The installed plugin runs from the tarball published under `dist/`; editing plugin sources does not change it or reload it. Install a newly packed artifact and restart the session when new plugin logic must run.
